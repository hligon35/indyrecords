# Supervised synthetic pilot acceptance plan

This is an executable preparation package, not authorization to deploy or use company records. Andrew and Q-Shred interfaces remain versioned synthetic CSV contracts at the user's direction. No vendor endpoint, real record, public shared-token service or operational mutation may be enabled.

## Entry conditions and ownership

A management sponsor identifies the test scope and operators. An identity administrator approves the Access policy and user/customer grants. A device administrator identifies the exact Zebra model, Android/DataWedge versions and Windows/WebView2 versions. A security reviewer records dependency disposition and signing requirements. All approval references start pending in evidence.template.json; repository code cannot approve them.

Use only c1–c4 fictional customers and the checked-in demo export fixtures. Local D1 uses the placeholder database binding. Install Node 24 and run npm ci at repository root, then npm ci in apps/mobile and apps/windows. Apply all migrations with npm run db:local and load scripts/seed-demo.sql locally. Keep Workers preview/public endpoints disabled. Never run a remote migration as part of these checks.

## Test sequence and expected evidence

1. Run npm test, npm run build:web, Worker packaging with --dry-run, Android test:build-deps/build:android/doctor, Android Kotlin checks, a complete synthetic test APK build and the Windows installer build. Record command, source commit, exit code and log/artifact SHA-256. The readiness gate requires both an Android bundle and APK. CI runs the core code checks on main; packaging artifacts require separate evidence.
2. Exercise local D1 with a provisioned synthetic manager, warehouse operator and viewer. Confirm cross-customer reads/exports and unauthorized mutations are denied, grants/deactivation take effect immediately, session expiry/revocation works and audit-storage failure withholds exported data. Check that source records remain unchanged.
3. Configure an approved test Access application protecting only /auth/login. Set ACCESS_ISSUER, ACCESS_AUDIENCE and ACCESS_LOGIN_ENABLED=true. READONLY_ALLOWED_ORIGINS must contain exact web/desktop origins. Native callbacks additionally require NATIVE_LOGIN_REDIRECTS=irmrmsdesktop://auth,irmrmsdemo://auth. Test web, Windows system browser and Android system browser sign-in, cancellation, wrong/replayed state/code, cold/warm native deep links and sign-out. Use vendor test identities only. Validate secure-storage expiry/removal and device-backup exclusion on Android. No provider was configured during repository implementation.
4. Enable SYNTHETIC_WORKFLOWS_ENABLED and SYNTHETIC_MANAGEMENT_ENABLED only in local .dev.vars. Use adb reverse for device access to the loopback API. Register a demo arrival; receive, stage, refile, retrieve, pick, dispatch, deliver and return it. Verify record/order versions, courier/recipient references, customer isolation and linked custody history. Archive the customer and confirm new intake/order creation stops while existing work can be completed.
5. Test the actual Zebra profile in keyboard and intent modes separately. Capture the package/signature association, action, Enter delivery, duplicate-burst behavior and foreground-only receiver behavior. Turn networking off, queue operations, restart the app, reconnect, retry an already accepted command and create a real version conflict against a second test operator. Confirm exactly-once acknowledgement, explicit conflict replacement and preservation of the rejected event. Do not treat a Hermes export or Kotlin compile as hardware acceptance.
6. Stage the Andrew and Q-Shred fixture files. Inspect accepted/rejected rows, hash, source timestamp, schema version, job ID and reconciliation results. Introduce missing rows, duplicate IDs/barcodes, different locations/statuses and a foreign-customer row. Confirm staging changes only integration_jobs, never records or a vendor system. Vendor-supported real contracts require separate discovery and approval.
7. Filter inventory/order/custody reports, export CSV/PDF, verify customer scope, UTC dates, pagination, complete row counts, safe CSV formula handling and readable printed pages. PDF uses built-in fonts and explicit U+ notation for non-ASCII characters; this limitation needs acceptance before multilingual use. CSV/JSON retain full text. Synchronous exports are capped at 1,000 rows; narrow the filters for larger datasets.
8. Run npm run verify:restore against local synthetic D1. The drill exports a consistent local backup and restores it into a separate SQLite database, checks integrity/foreign keys, and invalidates restored sessions and login codes. The original DB is unchanged. Keep backup artifacts private and excluded from Git. Test recovery in the approved environment separately.
9. Run npm run verify:pilot, optionally with -- --evidence=path/to/evidence.json. Evidence must name the current commit and hash actual platform proof files. The tool executes core checks, reports unverified external acceptance, and never turns on production readiness or mutations. Review the JSON with the named owners.

## Stop and rollback

Stop on any real-data discovery, unauthorized access, missing audit entry, wrong-customer result, lost/duplicated custody event, unreviewed conflict, corrupted queue or export discrepancy. Stop the local Worker, disable local write flags and preserve the failing synthetic event/job IDs and logs. Revert application code to the last approved Git commit if needed; do not overwrite source inventory or restore over an operational database. Any restored authentication store must revoke sessions/codes so recovery cannot revive previously revoked credentials.

## Exit conditions

The software demo can be marked verified only with passing checks tied to its source commit. A supervised operational pilot additionally requires independently reviewed identity/device/runtime/restore/security evidence, vendor-supported read-only contracts, signed artifacts and management approval. Current policy prohibits real records and production mutations, so productionReady and supervisedPilotReady remain false. Clearing those restrictions requires a separate explicit authorization and release review; changing an environment variable or editing a JSON approval is insufficient.
